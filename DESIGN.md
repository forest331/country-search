# DESIGN.md

## 1. Отмена устаревших запросов

Задание моделирует классический баг production-поиска: ответ на старый запрос приходит позже ответа на новый и перезаписывает актуальный результат на экране. Например, пользователь ввёл `sp`, затем быстро `spain`. Если ответ на `sp` придёт позже, чем на `spain`, на экране окажутся результаты для `sp` — хотя пользователь уже ввёл `spain`.

### Почему `AbortController`, а не флаг «актуальный ли ответ»

Флаг (`let latestQuery = query; ... if (query === latestQuery) render(results)`) **фильтрует** устаревший ответ постфактум. Это плохо по трём причинам:

1. **Запрос всё равно висит.** Трафик, соединение, серверная нагрузка — всё расходуется впустую.
2. **Окно гонки сохраняется.** Между резолвом промиса и проверкой флага есть microtask-окно, в котором устаревший ответ может быть отрендерен.
3. **Задание прямо запрещает этот подход.** В разделе «Чего делать не нужно»: «Не маскировать гонку запросов костылём вида "показывать только самый последний полученный ответ по таймстампу" без реальной отмены через AbortController».

`AbortController.abort()` **реально прерывает** запрос на сетевом уровне. В DevTools такой запрос помечается как `canceled`, промис отклоняется с `DOMException` с `name === 'AbortError'` — это позволяет легко отличить отмену от ошибки.

### Где именно вызывается `abort()`

Ключевое архитектурное решение: `abort()` вызывается **синхронно в обработчике `input`**, до того как `debounce` решит, запускать ли новый запрос:

```ts
input.addEventListener('input', () => {
  activeController?.abort(); // ← отмена немедленно
  activeController = null;
  // ...
  debouncedSearch(query);
});
```

Если бы `abort()` вызывался только внутри `debouncedSearch` (то есть через 400 мс после последнего символа), устаревший ответ успел бы прилететь в «окно ожидания debounce» и перезаписать экран. Задание прямо предупреждает об этом: «Отмена: при каждом изменении ввода (а не только в момент, когда debounce фактически запускает новый сетевой запрос)».

### Комбинирование сигналов: `AbortSignal.any`

`searchCountries` принимает один `signal`, но отменять запрос нужно по двум причинам: новый ввод и таймаут. Оба источника комбинируются в `performSearch`:

```ts
const combinedSignal = AbortSignal.any([
  signal, // отмена пользователем
  AbortSignal.timeout(timeoutMs), // таймаут
]);
```

`AbortSignal.any` срабатывает при срабатывании любого из переданных сигналов. Это позволяет не городить ручную связку `addEventListener('abort')` на каждом источнике.

### Различение `AbortError` и `TimeoutError`

В `catch` мы проверяем `error.name`:

- **`AbortError`** — пользователь изменил ввод, отмена наша собственная. Не ошибка, пользователю ничего не показываем (ранний `return`).
- **`TimeoutError`** — `AbortSignal.timeout` сработал. Настоящая ошибка, показываем сообщение с кнопкой «Повторить».
- **`HttpError`** — сервер ответил 5xx/4xx (кроме 404). Настоящая ошибка, показываем.
- **Всё остальное (`TypeError` от `fetch`)** — сетевой сбой. Настоящая ошибка, показываем.

Если путать `AbortError` и `TimeoutError`, получаем два плохих сценария: либо таймауты никогда не показываются (пользователь думает, что запрос «завис»), либо нормальная отмена выглядит как красный экран ошибки.

## 2. Обоснование задержки debounce

Выбрано **400 мс**. Обоснование:

- **Ниже 200 мс** — debounce почти не экономит запросы, пользователь печатает медленнее, чем срабатывает таймер. На каждый символ уходит запрос — это создаёт шум в Network и нагрузку на API.
- **200–400 мс** — оптимальный диапазон. Типичная скорость набора — 5–8 символов в секунду, то есть 125–200 мс между нажатиями. Debounce 300–400 мс успевает «схлопнуть» серию нажатий в один запрос.
- **Выше 600 мс** — поиск становится «laggy». Пользователь видит, что ввёл `spain`, но результаты появляются через ощутимую паузу.
- **Совсем убрать debounce** — каждый символ запускает запрос. Это не только нагрузка на сеть, но и повышает шанс гонки: чем больше запросов в полёте, тем чаще устаревшие ответы приходят позже актуальных.

**Итог:** 400 мс — компромисс между отзывчивостью и снижением числа запросов.

## 3. Сложность (Big O)

### `mapCountryResponse(raw)`

- **Время:** $O(L)$, где $L$ — количество языков страны. Мы проходим по массиву `languages` трижды (`.map`, `.filter`, `.join`), каждая операция — $O(L)$. Остальные поля читаются за $O(1)$. На практике $L \le 5$, так что фактически это константа, но формально — $O(L)$.
- **Память:** $O(L)$ — создаётся строка с названиями языков, длина которой пропорциональна суммарной длине названий.

### `searchCountries(query, signal)`

- **Время:** $O(1)$ по нашему коду (создание URL, `fetch`, проверка `response.ok`). Реальная сложность определяется сетью и сервером, не нами.
- **Память:** $O(R)$, где $R$ — размер ответа (массив стран).

### `debounce(fn, delay)`

- **Время:** $O(1)$ на каждый вызов `debounced()` — `clearTimeout` + `setTimeout`.
- **Память:** $O(1)$ — одна переменная `timerId` в замыкании.

## 4. Принципы чистого кода и где они применены

- **Единственная ответственность (SRP).** `searchCountries` (`src/core/searchCountries.ts`) отвечает только за сетевой запрос и проверку `response.ok`. `mapCountryResponse` (`src/core/mapCountryResponse.ts`) — только за преобразование «сырого» объекта в `CountryCard`. `performSearch` (`src/core/performSearch.ts`) — только за комбинирование сигналов. UI (`src/ui/app.ts`) — только за отображение. Никакой модуль не делает две вещи одновременно.
- **Чистые функции.** `mapCountryResponse` — чистая: один и тот же вход всегда даёт один и тот же выход, нет обращений к DOM, сети или глобальному состоянию. Легко тестируется на фикстурах.
- **Явная типизация ошибок.** `HttpError` (`src/core/searchCountries.ts`) — свой класс, а не «магический код» или `any`. Это позволяет в `catch` различать типы через `instanceof`, а не парсить сообщения.
- **Разделение логики и представления.** Вся async-логика (`debounce`, `searchCountries`, `performSearch`, `mapCountryResponse`) не зависит от DOM и тестируется в Node.js. UI (`src/ui/app.ts`) — тонкий слой, который только вызывает core-функции и обновляет DOM.
- **Безопасное создание DOM.** В `src/ui/app.ts` все элементы создаются через `document.createElement` + `textContent`. `innerHTML` / `insertAdjacentHTML` не используются нигде — это исключает XSS при работе с внешним API.
- **DRY-хелпер `el()`.** В `src/ui/app.ts` функция `el()` инкапсулирует создание элемента с классом и текстом. Без неё каждый рендер занимал бы 3–4 строки на один DOM-узел.

## 5. Семантика 404

`countries.dev` отвечает `404`, когда совпадений нет. Это не ошибка, а пустой результат. `searchCountries` распознаёт этот статус и возвращает `[]`. UI показывает нейтральное «Ничего не найдено» (серая карточка с иконкой 🔍), визуально отличное от красной карточки ошибки с кнопкой «Повторить».

Любой другой неуспешный статус (`500`, `503`, `429`) — настоящая ошибка. `searchCountries` бросает `HttpError` со статусом, UI показывает `Ошибка {status}. Попробуйте ещё раз.`

Браузер логирует `404` в консоль — это ожидаемо и не влияет на UX.
